# 279: Security review of what the 2026-11-25 sync's first review skipped

The first review of [sync-2026-11-25](sync-2026-11-25.md) covered process launches, RPC and MCP permissions, outbound network and telemetry, attachment parsing, webhooks, dependencies and CI. This one reads the other areas upstream changed in `cbd1f04bca..9df77f2125`, plus our worker gateway handlers. One defect fixed, one medium behaviour change left to a person, the rest no issue or low.

## Fixed

- **Choosing the worker gateway needed only `orchestration:operate`.** `agentd.setWorkerGateway` (ours, b007b25fc8, not upstream's) writes `dispatch.TOOL_base_url`, `--key-file` and `dispatch.TOOL_model` into agentd's config on this host, so every local worker sends its requests, and the gateway's key, to that gateway. Any session that can run threads (a default-access outside MCP client's grant, a paired device with operate) could switch it. It now needs `environment:maintain`, as `agentdSetMaxWorkers`, `agentdLowerPermissionMode` and the custom gateway changes do. The test in `RpcAuthorization.test.ts` fails without the fix (`expected 'orchestration:operate' to be 'environment:maintain'`).

Upstream files changed:

- `packages/contracts/src/clientRpcPermissions.ts`: `agentdSetWorkerGateway` guarded by `environment:maintain`, so the client refuses it too.
- `apps/server/src/auth/RpcAuthorization.ts`: its `orchestration:operate` entry removed, which overrode the guarded one.
- `apps/server/src/auth/RpcAuthorization.test.ts`: the scope asserted beside the other agentd config settings.

## Decisions on the first review's two low findings

- **HMAC signature per workflow webhook: not now.** Workflows are off in our product profile and Labs, and `WorkflowEngine` loads only when `workflowsEnabled` is on, so no hook URL exists in our builds. The URL token is random per hook and compared in constant time. Revisit with upstream if workflows are turned on.
- **Outside MCP clients with read access get every thread's milestones: kept.** `orchestration:read` already lets such a client list and read every thread of the environment (`thread_list`, `thread_read`), and milestones carry no more than those. Narrowing only the events would diverge from upstream without narrowing what the client can see; a per-client thread scope would be a new access level for all of them.
