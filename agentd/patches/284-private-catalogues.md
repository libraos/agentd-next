# 284 — Private plugin catalogues and a developer mode

Settings → Plugins lists catalogue sources. The official one (`libraos/plugins`) is always first and cannot be removed. A person adds any number of GitHub repositories (`owner/repo`, `github.com/owner/repo` or its URL) that hold a `catalog.json` in the same format; the app reads it on the default branch and refuses to add a source whose catalogue it cannot read, saying why. A private repository needs a read-only token for it (fine-grained, Contents: read). The token goes to the server's secret store (`ServerSecretStore`, name `agentd-plugin-source.gh~<owner>~<repo>`, a 0600 file) and nowhere else: `<stateDir>/plugins/sources.json` lists only repositories, and the listing a client gets says only whether a token is kept. Adding the same repository again with a token replaces it; removing a source deletes its token first (and stops if it cannot) and then its cached catalogue. Its installed plugins stay installed and keep running; the listing marks them `sourceRemoved` and the page says the source is gone and that they cannot be updated until it is added again.

With a token, every read of that repository goes through `api.github.com`: the catalogue (`/repos/R/contents/catalog.json`), the commit's tree and each file as a blob by its id (`/repos/R/git/blobs/SHA`), so the token never goes to the raw or codeload hosts. The token is put on a request only when its URL is `https://api.github.com/repos/<that repository>/…`; fetch's own redirect following is off (`redirect: "manual"`), and the app follows a redirect itself, without the token from the first redirect on, even one back to the API. An added catalogue installs only from its own repository: an entry pinned in another one is refused before anything is fetched (the official catalogue is not limited this way). Errors name the URL, not the token; Effect redacts the `authorization` header on spans. A source without a token is read like the official catalogue, anonymously from the raw host.

Pinning is the same for every source: each entry names one commit, and every file is checked against that commit's git tree (`downloadPinned` now takes how to fetch, so a token source reads blobs from the API).

Plugins are keyed per source. An official plugin's key is its bare id, as before, so its folder (`plugins/cache/libraos/<id>/<version>/`), settings, secrets, setup record and data folder do not move and installs from before this change keep working without a migration step. A plugin from a GitHub source is `gh~<owner>~<repo>~<id>`, installed at `plugins/cache/gh~<owner>~<repo>/<key>/<version>/`, so a plugin that finds its data folder from its own path (the redaction plugin does) gets `plugins/data/<key>/`, not the official plugin's. Settings, secrets, secret files, setup and per-project overrides all use the key, so a private plugin with an official plugin's id installs beside it and changes nothing of it. Hooks run, and MCP server names are taken, official plugins first, so another catalogue cannot run before an official hook or take an official server's name.

Developer mode (off by default, `sources.json`) adds a local folder as a plugin by its full path. The folder's `agentd-plugin.json` is checked by the same parser as an install (`parsePluginManifest`), and a refused manifest is reported with every reason. A local plugin is not copied or pinned: its key is `local~<id>`, its manifest is read again every time it is listed or run, and one that no longer parses is listed with its reasons and does not run. Read again on the page re-reads it. Removing it forgets the folder and never deletes it. With developer mode off, local plugins are neither listed nor run, and sends go on.

Provenance is shown wherever a plugin appears: a badge in the list (Official, OWNER (private), Local), the new install dialog (every install and update now asks first, with the source and whether LibraOS reviewed it), the before-send indicator (`Name (Source)`), and the MCP servers section (`Source: …`).

## Pasted links and the GitHub connection (follow-up)

The source field takes a link too (`parseSourceLink`): the repository (`github.com/O/R`, `.git`, `tree/BRANCH`), its `catalog.json` (`blob/…/catalog.json` or the raw host), or a plugin's folder (`github.com/O/R/tree/BRANCH/<path>`). Only https on github.com, www.github.com and raw.githubusercontent.com, with no user, password or port; anything else, a local path or `file://` included, is refused as invalid, so a link never selects a local folder. A folder link adds the source if needed and returns the plugin's key as `linked`, which opens that plugin's install dialog. It does so only when the catalogue lists an entry whose path the link's tree ends with and whose pinned repository is the link's; otherwise it is refused before anything is saved. The branch in the link is ignored: the install is the catalogue's pinned commit. An official plugin's link opens it without adding a source.

A private repository with no typed token reads with Next's own GitHub connection, the one Settings → Source control shows and the pull request and issue features use: `GitHubAppAccess.credentialFor` (the GitHub App's token where an installation covers the repository, else the account's own from Settings, the environment or `gh`). The GitHub driver exposes it as an optional `repositoryCredential(host, repository)` on `SourceControlDriverInstance`, and `AgentdGitHubConnection` reads it from the server's `SourceControlDrivers`, so there is no second credential reader. An anonymous read that answers 404 returns reason `githubConnection`; the page asks once for that source, naming the account discovery reports, and on confirm the source is saved with `githubConnection: true` in `sources.json` (choosing it removes a kept token; giving a token clears it). The credential is asked for at each fetch, only for a confirmed source, and goes through the same `getWithToken` as a typed token: only to `https://api.github.com/repos/<that repository>/…`, never across a redirect. Plugins never write, log or show it. With no connection the error (`connected: false`) says to sign in with GitHub or run `gh auth login`; the dialog shows Source control's own Sign in with GitHub panel (`SourceControlAppSignInSettings`) when the server offers the app sign-in, and the token field stays.

A source's catalogue is read at most once a day, like the official one; there is no refresh button, though adding the source again reads it at once. A repository renamed on GitHub answers the API with a redirect, which is followed without the token, so a private source has to be added again under its new name. A plugin's display name is not unique across sources; the hook block and review messages from the server name the plugin, not its source. The local folder is typed as a path (no folder picker), and a client with environment maintain can point developer mode at any folder the server can read and run what its manifest declares. That scope can already add a catalogue it controls and install from it, which runs code on the server too, so developer mode adds no new power; it is not limited to desktop or local clients. Local plugins whose data folder is derived from their path use `.data` in their own folder. Mobile does not list plugins. Tested on Linux only.
