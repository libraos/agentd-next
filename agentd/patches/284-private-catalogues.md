# 284 — Private plugin catalogues and a developer mode

Settings → Plugins lists catalogue sources. The official one (`libraos/plugins`) is always first and cannot be removed. A person adds any number of GitHub repositories (`owner/repo`, `github.com/owner/repo` or its URL) that hold a `catalog.json` in the same format; the app reads it on the default branch and refuses to add a source whose catalogue it cannot read, saying why. A private repository needs a read-only token for it (fine-grained, Contents: read). The token goes to the server's secret store (`ServerSecretStore`, name `agentd-plugin-source.gh~<owner>~<repo>`, a 0600 file) and nowhere else: `<stateDir>/plugins/sources.json` lists only repositories, and the listing a client gets says only whether a token is kept. Adding the same repository again with a token replaces it; removing a source deletes its token and cached catalogue and leaves its installed plugins until they are removed.

With a token, every read of that repository goes through `api.github.com`: the catalogue (`/repos/R/contents/catalog.json`), the commit's tree and each file as a blob by its id (`/repos/R/git/blobs/SHA`), so the token never goes to the raw or codeload hosts. The token is put on a request only when its URL is `https://api.github.com/repos/<that repository>/…`; fetch's own redirect following is off (`redirect: "manual"`), and the app follows a redirect itself, without the token from the first redirect on, even one back to the API. A catalogue entry pinned in another repository is fetched anonymously. Errors name the URL, not the token; Effect redacts the `authorization` header on spans. A source without a token is read like the official catalogue, anonymously from the raw host.

Pinning is the same for every source: each entry names one commit, and every file is checked against that commit's git tree (`downloadPinned` now takes how to fetch, so a token source reads blobs from the API).

Plugins are keyed per source. An official plugin's key is its bare id, as before, so its folder (`plugins/cache/libraos/<id>/<version>/`), settings, secrets, setup record and data folder do not move and installs from before this change keep working without a migration step. A plugin from a GitHub source is `gh~<owner>~<repo>~<id>`, installed at `plugins/cache/gh~<owner>~<repo>/<key>/<version>/`, so a plugin that finds its data folder from its own path (the redaction plugin does) gets `plugins/data/<key>/`, not the official plugin's. Settings, secrets, secret files, setup and per-project overrides all use the key, so a private plugin with an official plugin's id installs beside it and changes nothing of it. Hooks run, and MCP server names are taken, official plugins first, so another catalogue cannot run before an official hook or take an official server's name.

Developer mode (off by default, `sources.json`) adds a local folder as a plugin by its full path. The folder's `agentd-plugin.json` is checked by the same parser as an install (`parsePluginManifest`), and a refused manifest is reported with every reason. A local plugin is not copied or pinned: its key is `local~<id>`, its manifest is read again every time it is listed or run, and one that no longer parses is listed with its reasons and does not run. Read again on the page re-reads it. Removing it forgets the folder and never deletes it. With developer mode off, local plugins are neither listed nor run, and sends go on.

Provenance is shown wherever a plugin appears: a badge in the list (Official, OWNER (private), Local), the new install dialog (every install and update now asks first, with the source and whether LibraOS reviewed it), the before-send indicator (`Name (Source)`), and the MCP servers section (`Source: …`).

Not done: organisation-managed sources and allowed plugins (the issue's Later). A source's catalogue is read at most once a day, like the official one; there is no refresh button, though adding the source again reads it at once. A repository renamed on GitHub answers the API with a redirect, which is followed without the token, so a private source has to be added again under its new name. A plugin's display name is not unique across sources; the hook block and review messages from the server name the plugin, not its source. The local folder is typed as a path (no folder picker), and a client with environment maintain can point developer mode at any folder the server can read and run what its manifest declares. That scope can already add a catalogue it controls and install from it, which runs code on the server too, so developer mode adds no new power; it is not limited to desktop or local clients. Local plugins whose data folder is derived from their path use `.data` in their own folder. Mobile does not list plugins. Tested on Linux only.
